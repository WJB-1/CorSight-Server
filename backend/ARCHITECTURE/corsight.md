## 修订版技术方案

### 二、数据采集层（街景采集与上传）

#### 2.1 采集流程（修订）
采集人员在目标路段的**采集点**进行街景拍摄，覆盖该点的有效**采集范围**。系统需记录以下元数据：

- **地理坐标**：经纬度（来自OSM/高德地图）
- **拍摄方位角（Bearing）**：每张图片的朝向（0°~360°）
- **设备视场角（FOV, Field of View）**：拍摄设备的水平/垂直视场角，用于计算该张图片的实际**视野覆盖范围**（如水平FOV 90°、Bearing 0°，则覆盖 -45°~+45° 的扇形区域）
- **时间戳**：用于版本控制与数据时效性校验

FOV与Bearing共同决定该张街景图在真实世界中的**可视地理扇区**，后续用于匹配该视野内实际照到的道路元素。

#### 2.2 两步异步上传（修订）
1. **`POST /metadata`**：上传`point_id`、坐标、`images`列表（含`bearing`、`fov`、`description`）→ 返回`session_id`
2. **`POST /image`**：携带`session_id`、`bearing`、`fov`与图片文件 → 后端按`{point_id}_{bearing}_{fov}_{timestamp}.jpg`存储，更新会话状态

**注意**：上传完成后**不立即触发VLM推理**。图片与元数据进入**采集缓存池**，等待批量处理条件触发。

### 三、语义提取层（多Agent VLM架构）

#### 3.1 场景检索与分类（修订）
分类器不再仅依赖GPS坐标猜测场景，而是**基于实际视野内容**进行检索：

1. **视野地理扇区计算**：根据采集点坐标 + `bearing` + `fov`，计算每张街景图覆盖的真实地理扇区
2. **OSM元素检索**：在该扇区内检索OSM道路元素（way/node/relation），获取其类型标签（如`highway=steps`、`highway=crossing`、`bridge=yes`）
3. **高德路线规划检索**：调用高德路径规划API，获取该路段的`walk_type`（如人行横道、天桥、地铁出入口等）
4. **场景融合分类**：结合OSM元素类型 + 高德`walk_type`，确定该采集点的**场景类型**，并分发至对应专家Agent

> **示例**：某张图片Bearing 90°、FOV 80°，计算得覆盖正东方向扇区。在该扇区内检索到OSM `highway=steps` + 高德`walk_type=4`（人行横道），则分发至"台阶-人行横道联合Agent"，提示词强制关注"台阶数量、扶手、有声红绿灯"。

#### 3.2 语义标签双轨输出（不变）
Agent输出OSM标准标签 + 宽松富语义标签，分别注入地图与存入数据库。

#### 3.3 微RAG增强（不变）
将检索到的场景类型（如`walk_type=4` + `highway=steps`）作为上下文注入提示词。

#### 3.4 批量缓存与提示词构建（新增）
系统引入**采集缓存池**与**批量提示词构建器**，避免单点单张实时调用VLM：

**缓存池机制**：
- 缓存池按`session_id`或`batch_id`聚合街景图
- 触发条件（满足其一即触发）：
  - **数量阈值**：单个采集点上传图片达到N张（如8张全方向）
  - **时间阈值**：缓存超过T分钟（如30分钟）
  - **手动触发**：采集人员主动提交"完成采集"
  - **批量上限**：缓存池达到M个采集点（如50个点）自动触发，防止积压

**批量提示词构建流程**：
1. **池内数据聚合**：读取缓存池中所有待处理街景图及其元数据（坐标、bearing、fov、OSM元素、walk_type）
2. **分组构建**：按场景类型将街景图分组，每组调用对应专家Agent的提示词模板
3. **批量提交**：将同组内多张图片的URL/路径 + 统一场景上下文，打包为一个**批量推理任务**（JSONL格式），一次性提交至VLM API
4. **结果回写**：VLM返回批量结果，按`point_id`与`bearing`回写至MongoDB，标记状态为`pending`（待注入）

> **优势**：降低API调用次数（N张图合并为1次调用）、减少Token浪费（共享场景上下文）、支持离线采集后统一处理。

### 五、路径规划与预览层（用户端）

#### 5.1 语义路径规划（不变）
GraphHopper基于更新后的OSM地图与视障权重计算路径。

#### 5.2 视障RAG与路线预览（不变）
路径结果传入视障RAG模块，检索MongoDB宽松描述，注入LLM生成语音播报。

### 六、系统数据流总览（修订）

```
[采集人员] 
    ↓ 街景图 + 坐标 + bearing + fov
[两步上传API] → 图片存储 + Session管理
    ↓ 进入采集缓存池（不立即处理）
    
[批量触发条件满足] ←── 数量/时间/手动/上限
    ↓
[视野扇区计算] ←── 坐标 + bearing + fov
    ↓
[OSM元素检索 + 高德walk_type检索] ←── 基于实际视野内容
    ↓
[场景分类器] → 分发至多专家Agent
    ↓ 批量提示词构建（同场景分组）
[VLM批量推理]
    ↓
[OSM标准标签] ──────┐    [宽松标签] ──────┐
    ↓                │         ↓          │
[OSC补丁生成] → [OSM地图更新] ←┘   [MongoDB语义库] ←┘
    ↓                                    │
[GraphHopper权重重建] ←── 乒乓切换 ──────┘
    ↓
[语义路径规划API]
    ↓
[视障RAG检索] → [LLM] → [语音路线预览] → [视障用户]
```

### 七、关键技术决策（补充）

| 决策项 | 说明 |
|--------|------|
| **FOV参与视野计算** | 不假设固定视角，根据设备实际FOV计算地理扇区，确保检索到的OSM/高德元素与图片内容真实对应 |
| **基于视野内容检索场景** | 拒绝"GPS坐标猜场景"，通过bearing+fov扇区精确检索道路元素类型，Agent提示词更精准 |
| **缓存池批量处理** | 采集与推理解耦，支持野外弱网环境下先缓存、后批量处理，降低VLM成本与复杂度 |
