# 瞳心引航团队分工方案

> 本文档面向非技术背景的团队成员，用大白话描述每个人的工作内容、负责的模块、以及模块之间怎么"传话"。

---

## 一、先搞清楚系统里有哪些"人"在干活

我们的系统就像一个公司，有不同的部门在协作：

```
用户（视障人士）
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  手机上的App（Android）—— 成员谭睿负责                            │
│  ├─ 各种按钮、输入框、语音界面（UI布局）                        │
│  ├─ 调用高德地图显示路线                                       │
│  ├─ 调用百度语音让手机"说话"                                   │
│  ├─ 调用端侧功能（成员A和耀阳训练的模型）               │
│  └─ 通过网络和后端/Agent"聊天"                                 │
└─────────────────────────────────────────────────────────────┘
    │
    ▼ 通过网络传数据
┌─────────────────────────────────────────────────────────────┐
│  Agent大脑（云端服务器）—— 成员A负责                            │
│  ├─ 接收App发来的"我要去XX"请求                                │
│  ├─ 调用高德地图规划路线                                       │
│  ├─ 调用大模型分析街景图片、生成播报文案                        │
│  ├─ 把结果一段一段传回给App（像直播一样流式传输）               │
│  └─ 整体架构设计，确保各个模块能正常配合                        │
└─────────────────────────────────────────────────────────────┘
    │
    ▼ 通过网络传数据
┌─────────────────────────────────────────────────────────────┐
│  街景数据库（后端服务器）—— 成员华威负责                            │
│  ├─ 存储各个路口拍的8张方向照片                                 │
│  ├─ 根据位置查找附近有哪些危险点                                │
│  ├─ 提供数据给Agent分析                                        │
│  └─ 维护数据采集工具（用来上传新照片）                          │
└─────────────────────────────────────────────────────────────┘
    │
    ▼ 蓝牙/网络
┌─────────────────────────────────────────────────────────────┐
│  助盲项链（硬件）—— 成员谭睿负责                                   │
│  ├─ 挂在脖子上的摄像头，拍用户正前方画面                         │
│  ├─ 把画面传给手机App                                          │
│  └─ 手机通过蓝牙控制它开关、调亮度                               │
└─────────────────────────────────────────────────────────────┘
```

## 二、四个人的具体分工

### 成员A（你）—— 总设计师 + Agent大脑开发者 + 端侧模型训练者

#### 你负责的模块

**模块1：Agent大脑（最核心的"聪明"部分）**

这是整个系统的"司令部"。App把用户的请求发到这里，你负责让这里"聪明地"处理这些请求。

具体做什么：
- 写代码让Agent能接收App发来的导航请求（比如"我要去图书馆"）
- 调用高德地图API获取步行路线
- 把路线上的关键节点（转弯、过马路等）提取出来
- 调用大模型（千问/Gemini等）分析街景照片、生成适合盲人听的播报文案
- 把生成的播报文案一段一段"流式"传回给App（像微信语音条那样一段一段来，不用等全部生成完）
- 维护一个配置文件，管理用哪个大模型、API密钥等

**模块2：端侧小模型（和成员D一起）**

这是在手机上直接运行的AI模型，不需要联网，用来识别眼前的障碍物。

具体做什么：
- 和成员D一起，用YOLO等工具训练能识别"悬空树枝""共享单车挡路""台阶"等目标的模型
- 把训练好的模型转换成手机能运行的格式（TFLite）
- 写一些辅助脚本，比如批量处理图片、测试模型准确率等
- 给成员C提供"使用说明书"，告诉他怎么在App里调用这个模型

**模块3：整体架构设计**

- 设计整个系统的"骨架"，确保各个模块能正常通信
- 制定接口规范（就是"A模块给B模块传数据时，数据长什么样"）
- 协调其他成员的工作，解决模块对接时的问题

#### 你的模块要和谁"传话"

| 你和谁对接 | 通过什么"传话" | 传什么话 |
|-----------|--------------|---------|
| 成员B（后端数据库） | HTTP请求（就像浏览器访问网页一样） | 问B："这个坐标附近有什么危险点？" B回答："前方15米有红绿灯路口" |
| 成员C（App） | HTTP请求 + SSE流式传输 | C问你："我要去图书馆" 你回答："前方100米右转..."（一段一段说） |
| 成员D（一起训练模型） | 共享模型文件 + 脚本 | 你训练好模型给D测试，D发现问题告诉你调整 |

---

### 成员B —— 数据库管理员 + 数据采集团队 + 后端接口对接员

#### 成员B负责的模块

**模块1：街景数据库（系统的"记忆库"）**

这个模块负责存东西和查东西。就像图书馆的管理员，知道每本书在哪。

具体做什么：
- 维护数据库，存储每个路口拍的8个方向的照片（北、东北、东、东南、南、西南、西、西北）
- 写代码让外部能查询："给定一个GPS坐标，附近50米内有什么危险点？"
- 写代码让外部能上传新的采样点数据（照片+文字描述）
- 维护数据库索引，让查询速度快（不然查一次等好几秒）

**模块2：数据采集工具（用来"进货"的工具）**

用来往数据库里添加新数据的工具。

具体做什么：
- 维护一个网页或小程序，让志愿者可以上传路口照片
- 照片要按8个方向拍，工具要检查是否拍全了
- 上传时自动记录GPS坐标
- 上传后自动存到数据库

**模块3：对外接口（和其他模块"传话"的窗口）**

成员B要写好"窗口"，让成员A的Agent能来查数据。

具体做什么：
- 提供接口给Agent查询附近危险点
- 提供接口给Agent批量查询一条路线上有哪些危险点（还没做，需要新增）
- 未来服务器落实后，可能还要直接给App提供接口（现在先用Agent的接口代偿）

#### 成员B的模块要和谁"传话"

| B和谁对接 | 通过什么"传话" | 传什么话 |
|----------|--------------|---------|
| 成员A（Agent） | HTTP请求 | A问B："这个位置附近有什么？" B回答："有红绿灯、盲道断了" |
| 数据采集志愿者 | 网页/小程序上传 | 志愿者上传照片和位置，B存到数据库 |
| 成员C（App，未来） | HTTP请求 | C直接问B："我前面有什么危险？" B直接回答（现在是通过A中转） |

---

### 成员C —— App界面设计师 + 硬件对接员 + 端侧模型调用员

#### 成员C负责的模块

**模块1：App的各种界面（UI布局）**

这是用户直接看到和摸到的东西。成员C负责设计这些界面长什么样、怎么摆放按钮。

具体做什么：
- 设计语音输入界面（一个大按钮，按住说话）
- 设计地图界面（显示路线、当前位置）
- 设计导航信息面板（显示"还剩500米""下一个路口右转"）
- 设计历史记录界面（显示之前去过哪里）
- 设计设置界面（调音量、选语音等）
- 所有界面要考虑盲人的使用习惯：按钮要大、要有语音反馈、颜色对比要明显

**模块2：助盲小功能的UI**

除了导航，还有一些辅助功能。

具体做什么：
- 设计"识别眼前物体"功能的界面（按一下按钮，手机告诉用户前面是什么）
- 设计"读取文字"功能的界面（摄像头对准路牌，手机读出来）
- 设计"求助"功能的界面（一键呼叫紧急联系人）
- 这些功能现在只做界面，背后的"聪明"部分由成员A/D提供

**模块3：端侧小模型的接口兼容**

成员A和D训练好模型后，成员C要在App里"用起来"。

具体做什么：
- 在App里预留好调用模型的"接口位置"（就像预留插座，等插头插进来）
- 模型识别到障碍物后，App要震动+发出"滴滴"警报音
- 用户双击屏幕问"前面是什么"时，App要把摄像头画面传给云端大模型分析
- 写代码处理模型返回的结果（比如"前方1米有共享单车"），并转成语音播报

**模块4：助盲项链（硬件）**

挂在脖子上的摄像头，解放用户的双手。

具体做什么：
- 买ESP32-CAM开发板（带摄像头的小电路板）
- 写程序让它能连WiFi、开摄像头、传视频画面
- 写程序让手机通过蓝牙控制它（开关、调亮度）
- 把手机和项链"配对"，让App能收到项链传来的画面
- 设计项链的外壳（3D打印或找现成的）

#### 成员C的模块要和谁"传话"

| C和谁对接 | 通过什么"传话" | 传什么话 |
|----------|--------------|---------|
| 成员A（Agent） | HTTP请求 + SSE流式 | C问A："我要去图书馆" A一段一段回答导航播报 |
| 成员A/D（端侧模型） | 本地函数调用（在同一台手机里） | C把摄像头画面给模型，模型回答"有障碍物" |
| 助盲项链（硬件） | 蓝牙 + WiFi | C通过蓝牙告诉项链"开机"，项链通过WiFi传画面给C |
| 高德地图 | SDK调用 | C告诉高德"显示地图""规划路线"，高德返回地图数据 |
| 百度语音 | SDK调用 | C把文字给百度，百度返回语音播放 |

---

### 成员D —— 端侧模型训练师 + 测试员

#### 成员D负责的模块

**模块1：端侧小模型训练（和成员A一起）**

在手机上运行的AI模型，用来识别障碍物。因为要在手机上跑，所以模型必须"小而快"。

具体做什么：
- 和成员A一起收集训练数据（各种障碍物的照片，标注好"这是什么"）
- 用YOLO等工具训练模型（教模型认识"共享单车""树枝""台阶"等）
- 调整模型参数，让它在手机上跑得够快（0.1秒内出结果）
- 测试模型的准确率（100次识别，对了几回）
- 把模型"压缩"成手机能运行的大小（从几百MB压到几十MB）

**模块2：功能脚本工具**

写一些"小工具"脚本，方便上层调用。

具体做什么：
- 写脚本批量处理照片（调整大小、统一格式）
- 写脚本测试模型性能（测速度、测准确率）
- 写脚本把模型转换成不同格式（供不同手机用）
- 给成员C写"使用说明书"："调用这个函数，传入摄像头画面，返回识别结果"

**模块3：模型部署到手机**

把训练好的模型"装"到App里。

具体做什么：
- 把模型文件打包进App安装包
- 写代码让模型在App启动时加载到内存
- 写代码把摄像头画面"喂"给模型
- 处理模型的输出结果（比如画个框标出障碍物位置）

#### 成员D的模块要和谁"传话"

| D和谁对接 | 通过什么"传话" | 传什么话 |
|----------|--------------|---------|
| 成员A（一起训练） | 共享代码 + 模型文件 | A调好模型结构给D，D测试发现问题反馈给A |
| 成员C（App调用） | 函数接口文档 | D写说明书告诉C："调用analyzeFrame()，传入图片，返回结果" |

## 三、模块之间的"传话"总览（接口清单）

下面用大白话列出所有模块之间"传话"的方式：

### 1. App（成员C）→ Agent（成员A）

**传话方式**：像发微信消息一样，通过网络发送HTTP请求

**传什么话**：
- App说："用户现在在XX位置，想去图书馆，尽量避开天桥"
- Agent回答："好的，全程700米，前方100米11点钟方向上天桥..."（一段一段发，像语音条）

**接口长什么样**：
```
App发POST请求到：http://Agent服务器地址/api/navigation/preview
带着的数据：
{
  "origin": "116.434307,39.90909",      // 起点坐标
  "destination": "116.434446,39.90816",  // 终点坐标
  "user_voice": "我要去图书馆"            // 用户说的话
}

Agent返回（SSE流式，像直播）：
第一段："全程约700米，预计12分钟到达。"
第二段："前方100米，11点钟方向上天桥。"
第三段："下天桥后直行500米..."
...
```

### 2. Agent（成员A）→ 数据库（成员B）

**传话方式**：像查百度一样，发HTTP请求问数据

**传什么话**：
- Agent问："这个坐标附近50米有什么危险点？"
- 数据库回答："有3个点：15米处有红绿灯、40米处有共享单车挡路"

**接口长什么样**：
```
Agent发GET请求到：http://数据库服务器地址/api/navigation/nearby?lat=39.909&lon=116.397&radius=50

数据库返回：
{
  "points": [
    {"type": "crosswalk", "has_traffic_light": true, "distance": 15},
    {"type": "obstacle", "desc": "盲道被违停车辆阻断", "distance": 40}
  ]
}
```

### 3. Agent（成员A）→ 大模型（阿里云/谷歌等）

**传话方式**：像调用外卖平台的API，发请求等回答

**传什么话**：
- Agent说："这是8张街景照片，请分析这个路口对盲人有什么危险"
- 大模型回答："路口有红绿灯但无提示音，盲道在东南角断了，建议..."

**接口长什么样**：
```
Agent发POST请求到：大模型服务商的API地址
带着的数据：
{
  "model": "qwen-vl-plus",
  "messages": [
    {"role": "system", "content": "你是视障导航助手..."},
    {"role": "user", "content": [图片1, 图片2, ..., "分析这个路口"]}
  ]
}

大模型返回："该路口东南角盲道缺失，红绿灯无声音提示..."
```

### 4. App（成员C）→ 端侧模型（成员A/D）

**传话方式**：像在手机里两个App互相调用，不走网络

**传什么话**：
- App说："这是摄像头刚拍的一帧画面，看看有没有危险"
- 模型回答："检测到危险！前方0.8米有悬空树枝"

**接口长什么样**：
```java
// App调用模型的函数（成员D提供）
ThreatReport result = analyzeFrame(cameraFrame);

// 返回的结果
{
  "has_danger": true,           // 有没有危险
  "danger_type": "悬空树枝",     // 什么危险
  "distance_estimate": "0.8m",  // 多远
  "action": "TRIGGER_HAPTIC_BEEP" // 建议做什么（震动+蜂鸣）
}
```

### 5. App（成员C）→ 助盲项链（硬件）

**传话方式**：蓝牙像对讲机，WiFi像传视频

**传什么话**：
- App通过蓝牙说："开机！连上这个WiFi！"
- 项链通过WiFi传回："这是实时视频画面..."

**接口长什么样**：
```
蓝牙部分（像遥控电视）：
- App发送："打开摄像头"
- 项链回复："已打开，电量80%"

WiFi部分（像看监控直播）：
- 项链持续发送视频流到：http://192.168.43.x:81/stream
- App持续接收画面，传给模型分析
```

### 6. App（成员C）→ 高德地图

**传话方式**：调用高德提供的现成工具包（SDK）

**传什么话**：
- App说："显示地图""搜索北京西站""规划步行路线"
- 高德回答：地图数据、搜索结果、路线数据

### 7. App（成员C）→ 百度语音

**传话方式**：调用百度提供的现成工具包（SDK）

**传什么话**：
- App说："开始录音"（语音识别）
- 百度回答："用户说的是'图书馆'"
- App说："请说'前方右转'"（语音合成）
- 百度回答：语音文件，App播放出来

## 四、分工合理性分析

### 这个分工合理吗？

**总体来说，分工是合理的**，但有几点需要注意：

#### 合理的地方

1. **成员A管Agent + 架构设计**：Agent是系统的"大脑"，也是各个模块的"交通枢纽"，由总设计师负责是合理的。

2. **成员B管数据库 + 数据采集**：数据是系统的"粮食"，让一个人统一管理数据的"存"和"采"，避免数据格式混乱。

3. **成员C管App界面 + 硬件**：App和硬件都是用户直接接触的，让一个人负责能保证体验一致。

4. **成员A和D一起训练模型**：模型训练需要大量协作，两个人一起干比一个人干快，也能互相检查错误。

#### 需要注意的地方

1. **成员A的工作可能太多**
   - Agent开发本身就很复杂
   - 还要做架构设计、协调大家
   - 还要和D一起训练模型
   - **建议**：训练模型的具体工作主要由D承担，A负责把关关键决策

2. **成员C的工作跨度大**
   - 既要做App界面（软件）
   - 又要做硬件（ESP32-CAM）
   - 这两件事技能要求差别很大
   - **建议**：如果C硬件经验不足，可以先做App，硬件部分买现成的模块+简单组装

3. **成员B和A的边界要清晰**
   - B说"和Agent模块或者大模型交互"
   - 这意味着B可能也要写一些调用大模型的代码
   - **建议**：B只负责"查数据库"和"传数据"，调用大模型的逻辑统一由A负责，避免两个人写重复代码

4. **缺少测试和质量把控**
   - 分工里没有明确谁负责测试
   - **建议**：每个人负责测试自己的模块，A作为总设计师负责整体联调测试

## 五、每个人工作的"一句话总结"

| **成员B** | 管理系统的"记忆库"（数据库），维护"进货工具"（数据采集），写好"查询窗口"让Agent能查数据 |
| **成员C** | 设计用户看到的所有界面，让手机能调用"眼睛"（模型）识别障碍物，搞定挂在脖子上的摄像头 |

## 六、开发顺序建议

### 第一步：让Agent能"说话"（2-3周）

- 成员A：搭好Agent的基本框架，能接收请求、调用高德、返回结果
- 成员B：数据库跑起来，有基本的查询接口
- 成员C：App基本界面做出来，能输入目的地、显示地图
- 成员D：开始收集训练数据

**里程碑**：在App里输入"我要去XX"，能看到路线，Agent能返回文字播报

### 第二步：让Agent"聪明地说话"（2-3周）

- 成员A：接入大模型，让播报文案更自然
- 成员B：数据库里多存一些采样点数据
- 成员C：加入语音输入和语音播报
- 成员D：继续训练模型

**里程碑**：对着手机说"我要去图书馆"，手机语音播报完整路线

### 第三步：让手机有"眼睛"（3-4周）

- 成员A/D：端侧模型训练完成，能识别常见障碍物
- 成员C：在App里加入"识别障碍物"功能，检测到危险时震动提醒
- 成员B：继续完善数据库

**里程碑**：手机摄像头对准障碍物，能识别并语音提醒

### 第四步：解放双手（4-6周）

- 成员C：助盲项链做好，能传视频画面
- 所有人：整体联调测试

**里程碑**：戴上项链，全程不用拿手机，语音导航+障碍物提醒
